Beyond the Words

BM25 can only find emails that share your vocabulary. Ask it when you have to pay the solicitor and it will happily return an email about climbing grades. This walks through the fix — embeddings, cosine similarity, and rank fusion — using the real 606 vectors built over the 547 emails in data/emails.json.

The shape of the problem

The lexical ranker is a good one. It weights fields, saturates term frequency, normalises for length — all of the arithmetic in Inside BM25. And it has exactly one blind spot, which happens to be enormous: it can only score words that are in the query.

Here is a question a person would actually ask their own email archive, run against the real corpus through the real BM25F index. Nothing is invented; this is the top of the list.

The real failure

Rank 12 is off the first page. From the searcher's side this looks identical to "your archive does not contain this" — and that silence is the thing worth fixing. People remember what an email was about. Making them guess the sender's vocabulary first is a tax we can stop charging.

Idea one: meaning becomes coordinates

An embedding model is a function from text to a fixed-length list of numbers, trained so that text meaning similar things lands in similar places. We use OpenAI's text-embedding-3-small, which returns 1,536 numbers per input.

That is the entire idea, and it is worth sitting with how strange it is. There is no dictionary, no synonym list, no rules about "completion" meaning "handover". The model was trained on enough text that the position of a phrase encodes what it is about, and phrases about the same thing end up as neighbours whether or not they share a single character.

Idea two: nearness is an angle

Given two vectors, how close are they? Not by distance — text length and verbosity stretch vectors in ways that have nothing to do with topic. By angle. Two pieces of text pointing the same direction are about the same thing, however long or short they are.

The cosine of that angle is the score: 1.0 for identical direction, 0 for unrelated, negative for opposed. And because both vectors are already unit length, the cosine is just the dot product — multiply componentwise, add it up, done.

cos(q, d) = (q · d) / (‖q‖ ‖d‖)   →   q · d   when ‖q‖ = ‖d‖ = 1
score(d) = Σi=0…1535 qi · di   — one loop, 1,536 multiply-adds, no divisions

Normalising at build time rather than query time is the small design choice that makes the hot path this plain. The ranker never computes a magnitude.

Step zero, again: what exactly gets embedded?

BM25 had a tokenizer as its step zero. The semantic side has a chunker, and it is just as consequential — the model can only place text it is given, so what we hand it is what becomes findable.

Four decisions, all of them email-specific, all of them living in the adapter rather than the ranker.

The one email that needed splitting

Most emails here are short — median 434 characters — and a single vector represents them fine. Sixteen are not. The Exchange of Contracts letter runs to 6,660 characters and covers, in one message: the financial breakdown, the completion timeline, buildings insurance, which light fittings are included, where to collect the keys, and how to contact the council about council tax.

Averaged into one vector, all of that becomes a vague smear of "house admin" — near everything and close to nothing. So bodies over 1,500 characters are split on paragraph boundaries into ~1,200-character chunks with one paragraph of overlap, each carrying the subject line, and each embedded separately.

  1. 606 vectors from 547 emails. 531 emails are one chunk each; 16 long ones produce 75 between them.
    547 emails → 606 chunks → 606 × 1,536 floats = 930,816 numbers
  2. Chunks are ranked, emails are returned. Every chunk id is emailId#n. At query time each email takes the score of its best-matching chunk and the rest are discarded, so a six-chunk email cannot occupy six result slots.
    semantic top 8 (chunks) → Exchange#1, Exchange#2, Exchange#5, Exchange#4, Completion#0 … collapsed to emails → Exchange, Completion, Re: Completion, Conveyancing …
  3. Overlap keeps a point from being cut in half. The last paragraph of one chunk opens the next, so an idea spanning a paragraph break survives whole in at least one of them.

Honest about the threshold

1,500 characters was chosen from the corpus's own length distribution — median 434, p90 730, max 6,660 — and not from any measurement of whether retrieval actually improves at that point. It is a reasoned starting value awaiting an eval harness that does not exist yet. Same for the 1,200-character chunk size and the similarity floor further down.

Where the vectors live

Embedding is a network call, and 606 of them take a couple of minutes. Doing that per search would be absurd, so it happens once, in a build step, and the result is committed to the repository:

pnpm run build:vectors

Which raises the storage question. 930,816 floating point numbers written as JSON text — 0.005010511167347431, and so on — is more than 10 MB of digits, and every one of them has to be parsed back into a number on startup. Instead the whole block is packed as raw Float32 and base64-encoded.

  1. 4 bytes per number, not ~20 characters.
    606 × 1,536 × 4 bytes = 3,723,264 bytes → base64 ≈ 4.96 MB → file 4.99 MB
  2. One decode, not a million parses. Buffer.from(…, "base64") then a single Float32Array view over the bytes.
  3. A header that makes staleness loud. The file records the model, the dimension count, and a SHA-256 fingerprint of the exact texts that were embedded. Loading recomputes the fingerprint from the current corpus and throws if it differs.
    Vector artifact is stale: it was built with fingerprint 4a91c0…, corpus is 8fd233…. Run `pnpm run build:vectors`.

That last one is the difference between a bug you find and a bug you don't. Edit an email, forget to rebuild, and without the check search keeps working — quietly ranking against vectors for text that no longer exists. The fingerprint covers the embedded texts, not just the corpus file, so changing the chunking policy invalidates it too.

Searching: no index at all

BM25 needs an inverted index because scanning every document for every query term would be hopeless. The semantic ranker has no such structure. It compares the query to every single vector, in order, and sorts.

463 vectors × 1,536 dimensions = 711,168 multiply-adds — well under a millisecond

This is a deliberate non-decision. Approximate-nearest-neighbour indexes and vector databases exist to make this tractable at millions of vectors; at a few hundred they would add an operational dependency and approximation error to a scan that is already exact and instant. The rule of thumb we wrote down: revisit if the corpus grows by two orders of magnitude.

Why 463 and not 606

143 of the 606 chunks are byte-identical to another one. This corpus is somebody's real inbox, and real inboxes are full of automated post: sixteen copies of Your monthly statement is ready, fourteen of Your Spotify Premium receipt, each a separate email with its own id and its own thread.

Identical text embeds to an identical vector, so indexed individually they score identically and take the top sixteen slots as a block. Measured before this was fixed: mortgage pre-approval returned seven identical bank notifications in its top eight, with the two emails a person actually wanted at rank five and below. Worse than the lexical ranker it replaced.

So the index holds one representative per distinct text. This is not a display choice, and it is not deduplication of results — identical text should get one vote, not sixteen. The duplicates stay fully findable through BM25, which scores them on their own terms.

The floor: when nothing is close enough

A cosine ranker always has an answer. Ask it about quantum chromodynamics and it will dutifully return the least unrelated email in the archive, because something always has the highest score. That would turn today's honest empty page into a page of confident nonsense.

So results below a cosine floor are dropped. Here is what that floor is actually filtering, measured over all 606 chunks.

Two rankers, two incomparable numbers

Now the actual difficulty. We have two rankers with opinions about the same query, and their scores cannot be combined.

Reciprocal Rank Fusion

The way out is to throw the scores away entirely and keep only what both rankers agree on the meaning of: position. Being first means the same thing in both lists.

score(id) = Σrankings  1 / (k + rank(id))   rank is 1-based · k = 60 · absent from a ranking contributes nothing

That is the whole algorithm. Two properties fall out of it, and both are things we actually want:

  • Agreement wins. An email both rankers place mid-list beats an email one ranker puts first, because two moderate contributions add up.
  • A lone strong opinion still survives. A first place is worth 1/61 outright, enough to keep an obvious literal hit on the page even when the semantic ranker has never heard of it.

k is the dial between them. It flattens the difference between adjacent ranks — the bigger it is, the less a first place is worth relative to simply appearing in both lists.

Fusion, computed by hand

Real numbers, real query, the same one from Fig. 1. Both rankers are asked for 40 candidates; the semantic side clears its floor on 10 emails.

  1. Exchange of Contracts — lexical rank 12, semantic rank 1.
    1/(60+12) + 1/(60+1) = 0.013889 + 0.016393 = 0.030282
  2. Completion Confirmation — lexical rank 20, semantic rank 2.
    1/(60+20) + 1/(60+2) = 0.012500 + 0.016129 = 0.028629
  3. Re: Training goals — lexical rank 1, absent from the semantic list.
    1/(60+1) + 0 = 0.016393
  4. Re: Completion Confirmation — absent from the lexical top 40, semantic rank 3.
    0 + 1/(60+3) = 0.015873

Two mid-table lexical results, each endorsed by the semantic ranker, have overtaken the lexical winner — while the lexical winner keeps a place on the page rather than being deleted. Nothing about that ordering required knowing that 8.74 and 0.387 are on different scales.

What it must not break

Any change to relevance is a chance to make something that already worked worse. The thing most at risk here is precision: an email address, an invoice number, a distinctive surname. Those should land exactly, and semantics has nothing to contribute to them.

Measured: the query david.xu@firsthomemortgages.co.uk scores above 0.3 against 124 of 606 chunks. The embedding model can tell that the string is a mortgage-adviser's address, and so it gently likes every mortgage email in the archive — which is precisely the wrong behaviour for an identifier lookup.

It does no damage, because BM25 still ranks that address first and RRF respects that first place. The regression test asserting it is not a formality; it is the guard on the one thing this feature could plausibly have cost us.

Degrading, not breaking

If the embedding provider is down, or the API key is missing, the query path logs a warning and drops the semantic leg. Fusion then runs over a single ranking, which reproduces the lexical order exactly. Search gets worse; the page does not break. It is an explicit catch, not an accident — and it has its own test.

What it cannot do

  • Answer instantly. Every search now embeds the query over the network first — roughly 100–400 ms added to something that took single-digit milliseconds. Fine for a server-rendered page. If this ever becomes search-as-you-type, this number becomes the whole problem, and the fixes are debouncing, caching query vectors, or rendering lexical results immediately and folding semantic ones in when they land.
  • Know about anything added since the last build. The vectors are a committed artifact. A new email is lexically searchable immediately and semantically invisible until someone runs pnpm run build:vectors.
  • Explain itself. The UI shows a ranked list and nothing else — no score, no indication of whether an email surfaced lexically, semantically, or both. Deliberately out of scope, and the first thing to add if the ranking ever looks wrong to a user.
  • Guarantee thread diversity. Chunks collapse to their best per email, so no single email can flood the page. Nothing stops six different emails from one conversation doing it. Quote stripping makes this much rarer; it does not make it impossible.
  • Tell you whether any of this is tuned. The cosine floor of 0.3, the RRF constant of 60, the 1,500-character chunk threshold, and the field weights inherited from BM25 are all reasoned starting points. Nothing here measures relevance. evalite is installed with zero suites, and until it has some, "better" is an argument rather than a number.

The shape of the whole thing

  1. Build time. 547 emails → strip quotes, prepend subjects, split the long ones → 606 texts → one API call per 128 → 606 normalised vectors → packed base64 + fingerprint → data/email-vectors.json.
  2. Process start. Read the artifact once, validate its header against the live corpus, drop duplicate texts, decode into one flat Float32Array. Same memoisation as the BM25 index. A stale header throws here rather than degrading quietly.
  3. Per query. BM25F over the inverted index → 40 ids. In parallel conceptually, embed the query → 711,168 multiply-adds → apply the 0.3 floor → collapse chunks to emails → at most 50 ids.
  4. Fuse. Two id lists in, one ranked list out, by rank arithmetic alone. Slice to the page size. Hand back emails.

The lexical ranker did not change. The tokenizer did not change. The search page gained one await. Everything new landed behind the adapter seam that the BM25 work put there in the first place — which was the point of building it that way.
